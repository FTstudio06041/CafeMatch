Workstream 01 · 資料地基

探索頁 — 評分與評論系統

使用者能在探索頁對店家評分、留言，並成為推薦系統的訊號來源。

範圍

  • 入口：點開店家卡後的詳情內才出現，不在探索列表上
  • review 資料表（原始文字、預留標籤/情緒欄位、關聯 user + cafe + 時間）
  • 評分/評論 CRUD API
  • 店家詳情的評分輸入、評論列表、平均星等顯示
  • 基本濫用防護：需登入、送出 rate limit、後台可移除

職責

你主責schema 需三方對齊
review 資料表是與 NLP pipeline 的共用介面，建議在交接期間跟原負責人、NLP 負責人三方先把欄位敲定；不然之後改 schema 會連帶要改 pipeline。

Definition of Done

  • 從探索頁點開店家卡 → 詳情內可給 1–5 星並留文字評論
  • 同一使用者對同店只保留最新一則，可編輯/刪除
  • 店家詳情顯示平均星等、評論則數、分頁列表
  • schema 經三方確認後才建立
  • 具基本濫用防護且後台可刪違規內容

Workstream 02 · 探索體驗

探索頁 — 座標回填 + 自訂地圖

探索頁新增貼合站風的地圖，顯示店家位置；不嵌 Google 地圖。

範圍

  • 前置：用 google_place_id 批次 geocode 回填 lat/lng（新欄位 + migration + 一次性 script）
  • MapLibre GL + Protomaps（PMTiles 自 host）
  • 自訂 style JSON，色票對齊 --bg-main / --accent-color
  • 圖釘、hover、點擊→店家卡、縮放聚合 clustering、行動版效能
  • 地圖 ↔ 店家列連動：hover 卡片高亮圖釘、點圖釘定位/開卡
  • 桌機地圖 sticky、店家列獨立捲動；行動版地圖佔上緣可收合

職責

你主責
目前資料庫還沒有經緯度，只有地址與 place_id。回填是地圖能標點的根，所以會需要先做，再進地圖。

Definition of Done

  • 每家有效店家都有經緯度（附回填涵蓋率報告）
  • 地圖為自訂樣式，非預設 OSM 配色
  • 點圖釘可開店家卡；縮小時圖釘聚合
  • hover 店家卡高亮對應圖釘（地圖 ↔ 列表連動）
  • 桌機地圖固定、店家列可獨立捲動；行動版地圖可收合
  • 1000+ 圖釘不卡頓；行動版可用
  • 圖磚自 host，無外部 API key 依賴

Workstream 03 · 社群整併

店家頁 — 社群交流（篩選簡化版）

在每家店的頁面內讓使用者交流，而非把整頁社群搬過來；功能經取捨與簡化。

範圍

  • 決定保留哪些現有社群功能（貼文 / 留言 / 按讚 / 便利貼 四選幾）
  • 把交流綁定到單一 cafe，形成 per-cafe 討論串
  • 沿用既有 community_service / community models
  • 舊社群頁暫時下線（路由隱藏，資料保留可回復）
  • 基本檢舉與後台移除

職責

你主責保留清單由原負責人定案
這一項核心是取捨題不是搬運題：留什麼、砍什麼、為什麼，記得寫下來。保留/移除清單原負責人還沒定，開工前跟他確認一下想法就好。

Definition of Done

  • 每家店頁有一個「交流/討論」區，登入者可發言、按讚
  • 明確文件化保留/移除了哪些功能與原因
  • 舊社群頁入口移除、但資料保留可回復
  • 具基本檢舉/後台移除

Workstream 04 · 推薦核心

推薦系統 — GNN 整合

把既有 GNN 模型接進推薦流程，吃評分（權重）與評論標籤（NLP）作為訊號。

範圍

  • 評分 → user–cafe 邊權重
  • 評論 → NLP 抽標籤/情緒 → 節點特徵（NLP 專人負責，接手者對接介面）
  • 服務化：模型輸出如何存取（embedding 表 / 線上推論）、更新與重訓節奏
  • 冷啟動 fallback：資料不足時退回現有 cafe_retriever.py 的規則式檢索（依關鍵字/標籤比對挑店，不做個人化，簡單但穩定，一定撈得到店）
  • 建議加值：前後評估看板，比較 GNN vs 舊 retriever

職責

你負責整合模型 / NLP 有專人
模型與 NLP 有專人；你負責整合、冷啟動 fallback、與效果評估。評估看板現在完全沒有，加上去既實用又是紮實的一塊工作。

Definition of Done

  • 探索頁/推薦區能顯示 GNN 產出的個人化推薦
  • 新使用者/新店家有明確 fallback，不空白不報錯
  • 有可量化「新推薦是否優於舊 retriever」的指標或看板

Appendix A · 附錄

名詞說明

文件裡出現、但不一定人人熟的詞，用一兩句話講清楚。

推薦系統
依使用者過去的行為與偏好，主動挑出他可能喜歡的店，而不是等他自己搜尋。
GNN圖神經網路
一種在「圖」（節點 + 邊）上學習的模型。這裡把使用者、店家、標籤當節點，互動當邊，學出個人化推薦。本專案的核心。
retriever檢索器
從資料庫撈出候選店家的那段程式（見 cafe_retriever.py）。規則比對、不學習，是 GNN 冷啟動時的墊底方案。
RAG檢索增強生成
先「檢索」出相關資料，再交給 LLM「生成」回答。聊天推薦走的就是這個流程。
LLM大型語言模型
本專案用 Ollama 在自家機器跑的語言模型，負責把撈到的店講成自然語言回覆。
Ollama
在自己的機器上跑開源 LLM 的工具。專案裡所有 AI 呼叫都經由它（ollama_client.py）。
embedding嵌入向量
把使用者或店家壓成一串數字向量，向量越接近代表越相似。GNN 的輸出通常就是這種向量。
邊權重edge weight
圖上「使用者—店家」這條連線的強度。本專案用評分當作邊權重餵給 GNN。
節點特徵node feature
掛在節點上的屬性向量。評論經 NLP 抽出的標籤/情緒會變成店家節點的特徵。
冷啟動cold start
新使用者或新店家還沒有互動資料、模型算不準的情況。此時退回 retriever，避免推薦開天窗。
NLP自然語言處理
讓程式理解文字。這裡用來從使用者留下的評論裡抽出標籤與情緒。
MapLibre GL
開源的向量地圖渲染引擎，不綁 Google。本專案地圖（路線 B）用它來畫。
向量圖磚vector tiles
地圖資料以「可縮放的向量」而非圖片提供，因此能自由改顏色與樣式。
Protomaps / PMTiles
把某地區的向量圖磚打包成「單一檔案」自己 host，免 API key、樣式全自控。本專案地圖圖磚的起步方案。
style JSON
描述地圖長相（顏色、線寬、字體）的設定檔。改它就能把地圖換成符合站風的皮膚。
圖釘聚合clustering
地圖縮小時，把靠得很近的圖釘合併成一個帶數字的圈，避免擠成一團。
geocoding地理編碼
把地址或 Google place_id 換算成經緯度（lat/lng）。地圖標點前的必要一步。
migration / Alembic
資料庫結構變更的版本管理（migrations/ 資料夾）。加欄位、建新表都走它。
Definition of Done
「做到什麼程度算完成」的驗收參考線。每條工作線都附了一份。
Appendix B · 附錄

現有程式導覽

後端是 Flask + SQLAlchemy + MySQL，AI 走 Ollama；前端 React 19 + Vite。下面是接手會碰到的主要檔案，底色標示為推薦流程的核心。

入口 / 基礎

app.py
Flask 進入點，註冊各路由與擴充套件。
database.py · extensions.py
SQLAlchemy 實例，以及 OAuth 登入、限流、migrate 等擴充。
config/
常數與設定：ai_constants、prompts/（Prompt 模板）、settings。
migrations/
資料庫 schema 版本（Alembic）。W1 的 review 表、W2 的經緯度欄位都會在這裡加。

推薦 / 聊天 Pipeline（核心）

services/chat_pipeline_service.py
聊天推薦的總指揮，把下面各步驟串成一條流水線。
services/intent_classifier.py
用關鍵字表判斷訊息是否跟咖啡有關。
services/preference_service.py
呼叫 LLM 從對話裡抽出結構化偏好（純萃取，不做推薦）。
services/conversation_guide.py
對話引導狀態機，決定「這一輪 AI 該做什麼」、防止鬼打牆。
services/cafe_retriever.py
規則式檢索器，撈候選店。兩模式：關鍵字比對 / 加權情境。GNN 上線後這裡是 fallback。
services/ai_service.py
組裝 Prompt（政策 / 任務 / 輸出格式三層），交給 LLM。
services/ollama_client.py
呼叫 Ollama LLM 的底層 client。
services/situational_service.py
把情境選項解析成 tag_weights / 時間窗 / 價位，餵給加權檢索器。
routes/chat.py · routes/situational.py
聊天與情境元件的 API 端點。

探索頁（W1 · W2 主要落點）

routes/explore.py
探索頁 API（店家列表、照片）。評分/評論、地圖的新端點會加在這附近。
services/cafe_explore_service.py
組店家清單 + 使用者的收藏/去過狀態 + 卡片配色。
services/google_maps_service.py
取店家照片、補 place_id。W2 的座標回填可從這延伸。

社群（W3：將整併進店家頁）

routes/community.py
社群 API。整併後改為綁定單一店家。
services/post_service.py
貼文、按讚、留言。
services/note_service.py
便利貼（24 小時）、按讚、留言。
services/community_service.py
已棄用，僅保留相容；功能已拆到上面兩支。

其他服務

services/quiz_service.py
人格測驗計分。
services/user_service.py
刪除某使用者的所有資料（帳號清除用）。
services/cache_service.py
記憶體 LRU 快取；多 worker 部署時建議改 Redis。
services/settings_service.py
存在資料庫的 key/value 設定（如目前選用的模型）。
services/ollama_admin_service.py
模型健康檢查、取得預設模型。
services/admin_service.py
後台操作記錄與統計。W4 的評估看板可能落在後台。

資料模型 · models/

models/cafe.py
Cafes / Tags / cafe_tags / OperatingHours。W2 的 lat/lng、W1 的 review 表都會加在這一區。
models/user.py
User / UserShopState（收藏、去過）。
models/community.py
貼文 / 便利貼 / 按讚 / 留言。
models/quiz.py

models/system.py
系統設定、後台記錄、公告等。

一點小提醒：這四條線底下藏的深度（座標回填、投影與聚合、review→GNN 接縫、社群功能取捨、評估看板）其實比標題多不少。 每項的 Definition of Done 就是「做到哪算完」的參考線，對著它做可以避免不小心每項只做薄薄一層。

有兩件事，最好趁原負責人還在、交接期間先一起敲定：① review 資料表 schema（你 × 原負責人 × NLP 負責人）；② 社群保留/移除清單。這兩個卡在最前面，早點談定可以省掉後面不少返工。
